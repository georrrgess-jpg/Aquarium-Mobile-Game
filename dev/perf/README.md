# Performance measurements

Scenarios (identical for every build, `dev/perfbench.gd`, run with `dev/run_perf.sh [dir]`):

* **pool** - a fixed 14-step action sequence on a 32-creature board: selection taps (no turn), a Current preview
  opened and cancelled, slides, pair merges (some chain) and three Surges (preview + landing). Frames where the
  benchmark itself was planning its next input are excluded.
* **reef** - 30 residents idle for 10 s on the reef view, then 10 s on the pool's reef strip.
* **micro** - microseconds per call for the per-tap / per-action functions.
* **reef_visitor** (Update 3 build only) - 30 residents, 5 decorations, the Lantern Ray visiting, at Dawn and at Night.

Environment (both builds): Godot 4.3, **desktop measurements only**: Linux container, no GPU.
*headless* = script cost only, frame rate capped at 60 (anything over 16.7 ms is a script hitch);
*windowed* = 405x720 Xvfb window, software GL (llvmpipe): absolute numbers are far slower than a phone GPU and
mostly measure rasterisation, so use them for relative comparison only.

* `SUMMARY.md` - median [min-max] of 3 runs, before vs after (generated by `summarize.py`).
* `update1_baseline_x3.txt` - raw: Update 1 commit e0d72cb (via `git worktree`), 3 runs.
* `update3_final_current_x3.txt` - raw: the final build, 3 runs.
* `update1_baseline_same_harness.txt`, `update2_after_first_pass.txt` - single earlier runs (kept for the record).
* `baseline_update1.txt` - an earlier run of a first version of the harness.

Note: since Update 3 the pool's Surge weights depend on the tide phase, so the exact board after the sequence
differs slightly with the time of day the benchmark is run; the action count is the same.
